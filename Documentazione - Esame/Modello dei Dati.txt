Modello dati di JamPulse
Verifica sul codice del 28 ottobre 2026. Il database usa sette modelli Mongoose: User, Post, PostImage, Comment, Chat, Message e RefreshToken. I riferimenti sono ObjectId, tranne il collegamento applicativo tramite URL fra Post e PostImage.

1. Modello User (User.js)
Rappresenta l'utente registrato sulla piattaforma e gestisce sia le informazioni personali che le relazioni sociali di follow e la sicurezza delle credenziali. 
	username: String (Obbligatorio, Unico) — Nome utente univoco scelto in fase di registrazione. 
	email: String (Obbligatorio, Unico) — Indirizzo email dell'utente. 
	password: String (Obbligatorio) — Password dell'utente, memorizzata in modo sicuro sotto forma di hash tramite l'algoritmo bcryptjs (grazie a un middleware pre-save). 
	bio: String (Default: stringa vuota) — Breve descrizione o biografia del musicista. 
	instruments: Array di String (Default: array vuoto) — Lista degli strumenti musicali suonati dall'utente (es. Chitarra, Basso). 
	genres: Array di String (Default: array vuoto) — Generi musicali preferiti (es. Rock, Jazz, Funk). 
	following: Array di ObjectId con riferimento a User — Elenco degli utenti seguiti dall'utente corrente. 
	followers: Array di ObjectId con riferimento a User — Elenco dei follower che seguono l'utente. 
	role: String (Obbligatorio, enum: ['user', 'admin'], Default: 'user') — Ruolo e livello di autorizzazione dell'utente all'interno della piattaforma (RBAC). 'user' identifica i normali musicisti, mentre 'admin' garantisce privilegi di moderazione (eliminazione di qualsiasi post/commento) e gestione degli account utente.
	timestamps: Gestito automaticamente da Mongoose (createdAt, updatedAt). 
2. Modello Post (Post.js)
Rappresenta i contenuti multimediali o testuali pubblicati dagli utenti all'interno del feed sociale.
	userID: ObjectId (Obbligatorio, Riferimento a User) — Identificativo dell'autore del post. 
	content: String (Obbligatorio) — Il testo o la descrizione del post. 
	media: String (Default: stringa vuota) — URL dell'immagine opzionale, esterno oppure relativo /api/v1/uploads/<UUID.ext> per un file salvato in PostImage. Il collegamento non usa ref o ObjectId. La creazione accetta JSON o multipart con un file image alternativo a media; l'aggiornamento tramite PUT accetta solo i campi JSON content e media. Non sono presenti player audio/video.
	likes: Array di ObjectId con riferimento a User (Default: array vuoto) — Elenco degli utenti che hanno messo "mi piace" al post (gestito tramite logica di toggle). 
	timestamps: Gestito automaticamente (createdAt, updatedAt) per ordinare il feed dal più recente al più vecchio. 
3. Modello Comment (Comment.js)
Gestisce i commenti scritti dagli utenti sotto ai post.
	postId: ObjectId (Obbligatorio, Riferimento a Post) — Indica a quale post appartiene il commento. 
	authorId: ObjectId (Obbligatorio, Riferimento a User) — Indica quale utente ha scritto il commento. 
	text: String (Obbligatorio, trim: true) — Il testo del commento. 
	timestamps: Gestito automaticamente (createdAt, updatedAt) per l'ordinamento cronologico dei commenti. 
4. Modello Chat (Chat.js)
Rappresenta una conversazione privata. Il controller e l'interfaccia gestiscono chat tra due utenti; lo schema può contenere più riferimenti, ma non esistono funzioni applicative per gestire gruppi.
	participants: Array di ObjectId con riferimento a User — Elenco dei partecipanti. required: true è definito sui singoli elementi; non esiste un validatore che imponga almeno due partecipanti.
	timestamps: Gestito automaticamente (createdAt, updatedAt). Quando salva un messaggio, il controller aggiorna esplicitamente Chat.updatedAt. L'API ordina le chat per updatedAt decrescente; la pagina non riordina automaticamente la lista a ogni messaggio.
5. Modello Message (Message.js)
Rappresenta i singoli messaggi scambiati all'interno di una determinata chat.
	chatID: ObjectId (Obbligatorio, Riferimento a Chat) — Identificativo della conversazione di appartenenza. 
	senderID: ObjectId (Obbligatorio, Riferimento a User) — Identificativo dell'utente mittente del messaggio. 
	content: String (Obbligatorio) — Il testo del messaggio inviato. 
	timestamps: Gestito automaticamente (createdAt, updatedAt) per ordinare cronologicamente la cronologia della chat. 
6. Modello RefreshToken (RefreshToken.js)
Rappresenta le sessioni persistenti di autenticazione per l'implementazione dell'architettura "Dual-Token" (Access Token a breve scadenza e Refresh Token a lunga scadenza). Supporta la Token Rotation e la revoca del Refresh Token al logout: il token eliminato non può più rinnovare l'accesso. L'Access Token già emesso rimane valido fino alla sua scadenza; la revoca del Refresh Token non lo invalida immediatamente.
	token: String (Obbligatorio, Unico) — Valore del Refresh Token JWT firmato, salvato nel database. La firma ne protegge l'integrità; il contenuto non è cifrato.
	user: ObjectId (Obbligatorio, Riferimento a User) — Riferimento all'utente proprietario della sessione.
	expiresAt: Date (Obbligatorio) — Data e ora di scadenza ricavata dal claim exp del JWT e impostata dal controller. La durata predefinita è 7 giorni, configurabile tramite JWT_REFRESH_EXPIRES_IN; non è un default dello schema. È associata a un indice Time-To-Live (TTL) di MongoDB ({ expireAfterSeconds: 0 }) che elimina i record scaduti tramite un processo periodico in background, senza cron job applicativi. La verifica della scadenza del JWT non dipende dai tempi di rimozione del record.
	createdAt: Date (Default: Date.now) — Data e ora di creazione della sessione nel database.
7. Modello PostImage (PostImage.js)
Conserva le immagini caricate nella collezione postimages, separata da posts per evitare di leggere i binari nel feed.
	_id: String (Obbligatorio) — Nome UUID generato dal server con estensione jpg, png, gif o webp.
	data: Buffer (Obbligatorio) — Contenuto binario. Il limite applicativo è 5 MiB (5 × 1024 × 1024 byte); non è un validatore dello schema.
	contentType: String (Obbligatorio, enum: image/jpeg, image/png, image/gif, image/webp) — MIME ricavato dal formato riconosciuto dalla firma iniziale del file. Non viene decodificata l'immagine completa.
	timestamps: Gestito automaticamente (createdAt, updatedAt).
Il middleware Multer usa memoryStorage e accetta un file, due campi testuali e tre parti multipart. Il controller valida testo, tipo di media e alternativa file/URL prima del salvataggio del binario. La lettura GET /api/v1/uploads/:filename è pubblica, con nosniff e cache di un'ora. Un nome non conforme o un binario assente restituisce 404.
PostImage e Post sono salvati separatamente: in caso di errore nel salvataggio del post viene tentata la rimozione dell'immagine appena creata. Quando elimina un post, il controller rimuove il binario solo se nessun altro post usa lo stesso media; non c'è transazione. Cambiare media tramite PUT non elimina il binario precedente.
All'avvio migrateLocalPostImages importa solo i file locali di backend/uploads referenziati dai post e non già presenti in MongoDB; mantiene URL e originali. Il volume Docker post_uploads serve alla migrazione, mentre i nuovi file sono nel database. Installazioni collegate a database distinti non condividono le immagini.

Schema delle Relazioni (Riepilogo)
	User ↔ User (Social Graph): Relazione riflessiva a molti-a-molti tramite gli array followers e following. 
	User → Post: Relazione uno-a-molti (un utente può creare molteplici post). 
	User → Comment: Relazione uno-a-molti tramite authorId.
	User → Message: Relazione uno-a-molti tramite senderID.
	User ↔ Post (Like): Relazione molti-a-molti tramite l'array likes di Post.
	Post → Comment: Relazione uno-a-molti (un post può contenere numerosi commenti). 
	User ↔ Chat: Relazione molti-a-molti tramite l'array di participants. 
	Chat → Message: Relazione uno-a-molti (una chat contiene una sequenza di messaggi). 
	User → RefreshToken: Relazione uno-a-molti (un utente può possedere più sessioni/token attivi su diversi dispositivi).
	PostImage → Post: Un binario può essere riutilizzato da più post attraverso lo stesso URL media; un post può anche non avere immagine o usare un URL esterno. Non esiste vincolo referenziale Mongoose.

Vincoli applicativi e limiti
Le scelte strumenti/generi del frontend non sono enum del modello User. La registrazione normalizza email in minuscolo e username con trim; lo schema non impone questa normalizzazione.
La rotazione dei Refresh Token legge e cancella il record con operazioni separate: non garantisce consumo atomico fra client concorrenti. Il ruolo REST proviene dall'Access Token e resta quello emesso fino al rinnovo o alla scadenza.
Non sono presenti cascade generali: eliminare un utente non elimina post, commenti, messaggi, relazioni follow e Refresh Token; eliminare un post non elimina i commenti; eliminare una chat non elimina i messaggi.
Il seed svuota User, Post, Comment, Chat e Message, ma conserva RefreshToken e PostImage e può lasciare record senza riferimenti attivi.
